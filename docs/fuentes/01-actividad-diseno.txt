1. Activity Purpose
Once the team has specified and audited the software requirements, the next step is to transform those requirements into a technical and structural design for the proposed solution.

In this activity, students will define how the software solution will be built, including its architecture, technology stack, application components, user interfaces, data structures, database design, integrations, security considerations, and other technical decisions required before implementation begins.

The objective is not to start programming yet. Students must first establish a sufficiently detailed design that allows another development team to understand the proposed solution and begin implementation with minimal ambiguity.

The design must be directly supported by the requirements previously identified.

2. Learning Objectives
By completing this activity, students will be able to:

Transform software requirements into a coherent technical design.
Select and justify an appropriate technology stack.
Define the system's overall software architecture.
Identify the principal software components and their responsibilities.
Design the system's data model and database structure.
Create appropriate UML and architectural diagrams.
Design initial user interfaces through mockups or prototypes.
Identify APIs, external services, and system integrations.
Incorporate security, scalability, performance, accessibility, and maintainability considerations into the design.
Establish traceability between requirements and design decisions.
Identify technical risks and unresolved design decisions before implementation.
Produce a design package that can serve as the technical baseline for the development phase.
3. Important Principle
Students should follow this relationship:

Requirements → Design → Implementation → Testing → Deployment

The design must not introduce functionality simply because the team thinks it would be useful.

Every significant design element should be traceable to:

a functional requirement,
a non-functional requirement,
a business/user need,
a technical constraint,
or a justified architectural decision.
4. Activity Instructions
Each team must create a Software Solution Design Document for its project.

The document should contain the following sections.

4.1 Design Introduction
Briefly describe:

Project name
Problem being addressed
Solution being designed
Design objectives
Scope of the design
Relationship with the previously approved requirements
Students should explicitly identify the version of the requirements specification used as the basis for the design.

5. System Architecture
Students must define the overall architecture of the solution.

5.1 Architectural Style
Select and justify an appropriate architecture, for example:

Layered architecture
Client-server
MVC
REST API architecture
Monolithic architecture
Modular monolith
Microservices
Event-driven architecture
Serverless
Hybrid architecture
The team must explain why the selected architecture is appropriate for its project.

5.2 High-Level Architecture Diagram
Create a diagram showing, at minimum:

Users/actors
Frontend/client
Backend/application
Database
External systems/services
APIs or communication mechanisms
Major architectural components

  ▼

  │
  ▼

  ├── Authentication
  ├── Business Logic
  ├── Notifications

  └── AI / Analytics
  │

  │

The actual architecture must be adapted to each project.

6. Technology Stack
Students must define the technologies they intend to use.

Create a table such as:

Layer	Technology	Purpose	Justification
Frontend	React	User interface	Component-based UI
Backend	Node.js + Express	REST API	Existing team expertise
Database	PostgreSQL	Persistent data	Relational data requirements
Authentication	JWT	User authentication	API-based architecture
Testing	Jest	Automated tests	Unit/integration testing
Deployment	Render	Application hosting	Suitable deployment environment
Students should define, when applicable:

Frontend technology
Backend technology
Programming languages
Frameworks
Database
Authentication mechanism
APIs
Testing technologies
Version control
Hosting/deployment platform
Cloud services
AI/ML technologies
External APIs
Monitoring/logging tools
Technology Selection Requirement
For every major technology, students must provide a technical justification.

Avoid statements such as:

"We selected React because it is popular."

Instead:

"React was selected because the solution requires reusable interface components and frequent updates to interactive data views."

7. System Components and Modules
Identify the major components/modules of the system.

For each component, specify:

Component	Responsibility	Related Requirements	Dependencies
Authentication	Manage user login and access	FR-01, NFR-SEC-01	User database
Student Management	Manage student information	FR-05–FR-09	Database
Alert Management	Generate and manage alerts	FR-15–FR-20	Student data, AI module
Students should avoid defining modules merely according to programming convenience.

The decomposition should reflect the business and technical responsibilities of the system.

11. Data Design
Students must identify the principal data that the system needs to store and process.

Create a Data Dictionary containing relevant attributes.

Entity	Attribute	Data Type	Required?	Description	Constraints
Student	student_id	Integer	Yes	Unique identifier	PK
Student	name	VARCHAR	Yes	Student's name	2–100 chars
Student	email	VARCHAR	Yes	Institutional email	Unique
Student	birth_date	DATE	No	Date of birth	Valid date
The data dictionary should correspond to the requirements.

15. Non-Functional Requirements → Design
Students must explicitly demonstrate how the design addresses important non-functional requirements.

Create a table:

NFR	Requirement	Design Decision	How It Will Be Verified
Performance	Response < 2 sec	Database indexes + optimized queries	Performance test
Security	Only authorized users access reports	RBAC	Security test
Availability	System available during school hours	Cloud deployment + monitoring	Availability monitoring
Usability	Users complete registration easily	Simplified workflow	Usability test
This section is particularly important because it prevents students from treating non-functional requirements as merely descriptive statements.

19. Traceability: Requirements → Design
This is a critical component of the activity.

Students must create a preliminary Requirements-to-Design Traceability Matrix.

Requirement	Architecture Component	UI	Database	API	Diagram
FR-01	Authentication	Login	User	POST /login	Sequence 01
FR-02	Student Module	Student Form	Student	POST /students	Sequence 02
FR-15	Alert Module	Alert Dashboard	Alert	GET /alerts	Sequence 03
This allows the instructor to verify that the design actually responds to the previously specified requirements.

20. Technical Decisions and Design Rationale
Students must document important design decisions.

Use a simple Architecture Decision Record (ADR) format:

Decision	Alternatives	Selected Option	Rationale	Consequences
Database	MySQL / PostgreSQL / MongoDB	PostgreSQL	Relational data and constraints	Requires relational schema
At least five significant technical decisions should be documented.

21. Technical Risks and Open Questions
Before development begins, students must identify unresolved technical issues.

ID	Technical Risk / Question	Impact	Probability	Proposed Action	Responsible
TR-01	External API availability	High	Medium	Create fallback mechanism	Backend team
TR-02	Insufficient training data	High	High	Evaluate available datasets	AI team
The objective is to discover design problems before they become implementation problems.
